# HF-27-05 — Development + validate loop + review cruzada

Papel: economy · Depende de: HF-27-02, HF-27-03 · Resolve: D2, D6.

## Development (`core/line/stage_build.py::DevelopmentStage`)
Para cada ticket de `tickets.json` ainda sem commit `DarkFac-Job: <run>:<ticket>`, em ordem:
1. Agente em modo **write** (cascata `development`) no worktree, com o prompt `prompts/develop.md`: SPEC, o ticket, `acceptance`, `tests_to_add`, os comandos do projeto, `review-N.md` e o último `validate` falho, se houver, mais a instrução "escreva/ajuste testes primeiro; não altere .darkfac/runs".
2. Roda `commands.setup` (uma vez por worktree, com cache por hash do lockfile) e depois `commands.validate`.
3. Se falhar: resume o log. Usa `core/harness/test_subagent.py` (DistilledTestReport) ou, se ele não servir, os últimos 150 linhas + as linhas com `FAIL|Error`. Grava `validate-<ticket>-<i>.log.md` e volta ao passo 1 com o resumo. Até `run_caps.validate_iterations_per_ticket` (3).
4. Se passar: `commit` com trailer e `push`. Grava em `progress.json` o harness que implementou (usado pelo review).
5. Esgotou as iterações: se o erro indica spec impossível (o agente responde `SPEC_CONFLICT:` no texto), devolve `replan`. Senão, `failed(cause=validate_exhausted)` com o resumo. HF-27-08 transforma isso em notificação e não em loop.
6. Se `validate` estiver vazio (projeto sem testes): o primeiro ticket recebe a instrução extra "crie a infraestrutura mínima de testes e um teste para este ticket". Depois `detect_commands` é recalculado.

`output_refs=[head_sha]`. O job é retomável: se cair no meio, a próxima execução pula os tickets já commitados.

## Validation (`stage_build.py::ValidationStage`)
Determinística e sem LLM: faz clone limpo do tip da branch em diretório temporário, roda `setup` + `validate` + `build` e grava `validation.json` (comandos, exit codes, duração, SHA). Falha → `retry` para `development` (iteração+1) com o log resumido. Isso pega "funciona na worktree suja, quebra limpo".

## Review (`core/line/stage_review.py`)
1. `git diff origin/<default>...HEAD`. Se o diff for maior que 60 KB, envia só o sumário + arquivos de maior risco.
2. Agente em modo **read**, de **família diferente** da registrada em `progress.json` (regra `other_family_than_development`). O prompt `prompts/review.md` pede JSON: `{"verdict":"approve|changes_required","blocking":[{"file","line","issue","fix"}],"non_blocking":[...]}`. Só é bloqueante: bug de correção, teste que não testa o aceite, requisito do ticket não atendido ou quebra de contrato.
3. `changes_required` → grava `review-<n>.md` e retorna `retry` para `development`, até `run_caps.review_rounds` (2). Na terceira vez, aprova com `non_blocking` registrados, se a validação estiver verde, e anota no REPORT. Isso evita loop entre modelos com opiniões diferentes.
4. `approve` → commit de `review-<n>.md` e `success`.

## Aceite (repo temporário + agente falso que edita arquivos)
- Um ticket cujo teste falha 1x e passa na 2ª gera um commit, dois logs e `success`.
- Um teste que nunca passa: após 3 iterações, `failed(validate_exhausted)`, sem commit do ticket.
- Com `validate` vazio, o prompt contém a instrução de criar testes.
- A validação limpa detecta um arquivo não commitado necessário ao teste.
- O review usa a família oposta. `changes_required` gera `retry` com `review-1.md`, e o 3º `changes_required` com validação verde vira approve anotado.
