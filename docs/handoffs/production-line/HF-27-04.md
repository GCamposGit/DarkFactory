# HF-27-04 — Grill de rodada única + Planning com SPEC, tickets e marcos

Papel: economy · Depende de: HF-27-02, HF-27-03 · Resolve: D2, D7, D10.

## Grill (`core/line/stage_grill.py`)
1. `checkout` do workspace. Grava `DEMAND.md` com o texto do intake, o projeto e o canal.
2. Agente em modo **read** (cascata `grill`) no cwd do repo, com o prompt `prompts/grill.md`. O prompt pede que ele leia README/AGENTS/código e devolva **JSON**:
   ```json
   {"questions":[{"id":"q1","text":"...","kind":"business|intent|secret|account|technical",
                  "options":["A","B"],"recommended":"A","why":"..."}],
    "assumptions":["..."], "is_product_scale": false}
   ```
   Máximo de 5 perguntas.
3. As `technical` são resolvidas na hora pelo `recommended` e registradas em `GRILL.md` como premissa.
4. As `business|intent|secret|account` são enviadas **numa única mensagem** Telegram (owner bot), com botões por opção (reusar `cb:grill:<ticket>:<choice>` de `core/integrations/telegram.py`). O resultado é `waiting_human` com `deadline = now + 12h`.
5. Na resposta (handler Telegram já existente → `submit_grill_answers`) ou no deadline, o reconciliador re-enfileira o grill. O grill então completa `GRILL.md`: respostas reais, ou recomendadas marcadas `default_after_timeout`. `secret|account` **não** recebem default e viram `HumanRequest` (HF-27-08), bloqueando só os jobs que dependem deles (deploy, normalmente).
6. Sem perguntas bloqueantes: `success` imediato (sem esperar humano).
7. Commit + push. `output_refs=[commit_sha]`.

## Planning (`core/line/stage_planning.py`)
1. Agente em modo **read**, cascata `planning` (Opus, esforço alto), prompt `prompts/planning.md` com DEMAND + GRILL + comandos do projeto (HF-27-01). Ele produz:
   - `SPEC.md`: objetivo, fora de escopo, design curto, arquivos a tocar e riscos.
   - `tickets.json`: `[{id, title, goal, files_hint[], acceptance[], tests_to_add[], smoke[]}]`, com 1–6 tickets, cada um pequeno o bastante para uma sessão de agente.
   - Se `is_product_scale` ou mais de 6 tickets: `milestones.json` `[{title, demand_text}]`. **Só o marco 1** vira `tickets.json` deste run. Os demais são submetidos pelo intake existente (`AutonomousIntakeService.accept`) como demandas filhas com `depends_on=<run_id>` e `external_id=<run_id>:m<N>` (idempotente). O Grill das filhas herda o `GRILL.md` do pai e só pergunta o que for novo.
2. Validação determinística do JSON (Pydantic). Se for inválido, reprompt 1x com o erro. Se falhar de novo, `failed(cause=plan_invalid)`.
3. Commit + push. `output_refs=[commit_sha]`.

## Prompts (`core/line/prompts/*.md`)
Templates versionados, com placeholders `{demand}`, `{grill}`, `{spec}`, `{ticket}`, `{commands}`, `{lessons}`. `{lessons}` = últimas 20 linhas de `.darkfac/LESSONS.md` do repo alvo, se existir (memória barata, sem pipeline HF-10 no caminho crítico).

## Aceite
- Com agente falso: demanda clara gera 0 perguntas bloqueantes, `GRILL.md` só com premissas e `success`.
- Demanda com pergunta de negócio: 1 mensagem enviada, `waiting_human`. Sem resposta após o deadline simulado, segue com o recomendado e registra `default_after_timeout`. Pergunta `secret` nunca recebe default.
- Planning com JSON inválido duas vezes: `failed(plan_invalid)`.
- `is_product_scale`: N-1 demandas filhas criadas uma única vez (replay não duplica).
