# HF-27-09 — Topologia: imagem VPS com CLIs + workers on-prem via Postgres

Papel: operations · Depende de: HF-27-03 · Pode correr em paralelo com a onda 2.

## Objetivo
Rodar o mesmo `cloud_worker` em três hosts com capabilities diferentes, todos puxando do mesmo Postgres. Sem push HTTP síncrono da nuvem para on-prem.

| Host | Caps esperadas | Slots |
| --- | --- | --- |
| VPS (Hetzner CX23) | git, gh, node, python, harness:claude, harness:codex | **1** (CX23: 2 vCPU, 4 GB). 2+ só após upgrade |
| Desktop (i7 HX, 32 GB) | + harness:grok, harness:antigravity, target:local_service, gpu | 3 |
| Notebook | subconjunto do Desktop | 1–2 (fallback) |

Prioridade VPS > Desktop > Notebook: o worker com mais prioridade faz poll a cada 2 s, e os outros a cada 10 s e 20 s, e só claimam jobs com `ready_age > 30 s` (config). Assim o Desktop só atua como primário quando a VPS não claima (sem caps ou saturada). Isso é config pura (`DARKFAC_WORKER_PRIORITY`), com filtro por `ready_age` no `claim` (param opcional).

## Mudanças
1. `deploy/dokploy/Dockerfile.cloud`: instalar `git`, `gh`, Node LTS, `@anthropic-ai/claude-code`, `@openai/codex` (versões fixadas) e `lftp`. Volume persistente `/home/darkfac/.codex` (auth.json) e `/workspaces`. `CLAUDE_CODE_OAUTH_TOKEN` via env/secret do Dokploy.
2. `docker-compose.cloud.yml`: worker com `DARKFAC_WORKER_CAPS`, `DARKFAC_WORKSPACES=/workspaces`, limites de memória (worker 2 GB; o owner reduziu de 2.5 GB em 2026-09-23 para deixar folga no CX23) e `max_slots=1`.
3. **Bootstrap de login sem SSH manual:** comando `python -m core.line.auth_bootstrap codex`, executável pela fábrica via endpoint ops já existente ou `docker exec`. Ele roda `codex login --device-auth`, captura URL + código e envia pelo Telegram como `HumanRequest(kind=account)`, com probe `codex login status`. Para o Claude, o `HumanRequest` explica `claude setup-token` no Desktop e onde colar no Dokploy, com probe `claude -p ok`.
4. On-prem: `scripts/start_onprem_worker.ps1` passa a iniciar `python -m core.orchestrator.cloud_worker` com `DATABASE_URL` do Postgres **via Tailscale**, `DARKFAC_WORKER_CAPS` autodetectadas e `DARKFAC_WORKER_PRIORITY`. Reusar `install_onprem_worker_service.ps1` / `install_onprem_worker_user_startup.ps1` para ficar de pé após reboot.
5. Postgres acessível só pela interface Tailscale (bind no IP tailnet ou firewall por interface). Isso é pré-requisito humano: auth key do Tailscale (plano §7.4).

## Plano B (se o login por assinatura na VPS não se sustentar)
Não muda código: a VPS fica com caps sem `harness:*` (só `git`, `gh`, deploy, validation) e o Desktop claima development/planning/review. As etapas determinísticas (validation, integration, deploy, smoke) continuam 24/7 na VPS. Quando o Desktop desliga, o Notebook assume. Se ambos estiverem desligados, os jobs de agente esperam, e o painel mostra "sem worker com harness".

## Aceite
- `docker run <img> claude --version && codex --version && gh --version && git --version` passam.
- Três workers com caps distintas: job `target:local_service` só vai ao Desktop, e com a VPS parada o Desktop pega development em até 30 s + poll.
- O probe de auth falho no boot remove `harness:x` das caps publicadas (sem claim de job que vai falhar).
