## 2. `core/orchestrator/cloud_worker.py`
- `dispatch_claimed_job` passa a montar o `StageContext` (claim + projeto + `run_id`) e chamar `registry.dispatch(context)`. O resultado vai para `store.finish` + `materialize_result` como já é hoje. Sai o bloco de prompt genérico e o artefato `<stage>_deliverable.json` como resultado de etapa (ele pode continuar como recibo, mas nunca define sucesso).
- Heartbeat do lease numa thread enquanto o handler roda (agentes levam até 30 min). Se o Codex já implementou isso no HF-03-08, reaproveitar.
- `capabilities` do worker vêm do env `DARKFAC_WORKER_CAPS` + autodetecção: `git`, `gh`, `node`, `python`, e `harness:<x>` para cada CLI encontrado **e autenticado** (probe barato no boot e a cada 1 h: `claude -p "ok"`, `codex login status`). O worker publica as caps no heartbeat, para o painel mostrar "sem worker com harness:claude".
- `retry` com `not_before`: o store já tem ou precisa respeitar esse campo no `claim`. Se não tiver, adicionar a coluna nos dois adapters (SQLite e Postgres), numa mudança mínima.

## 3. `core/workflow/successors.py` (DAG enxuto)
- `PRODUCTIVE_DAG` da linha: `grill→planning→development→validation→independent_review→integration→build_deploy→(target_journey)→retrospective`.
- `retry` com `target_stage` (novo campo opcional em `StageResult`, ou convenção em `cause_code="retry:development"`): volta para a etapa indicada com `iteration+1`, carregando o log por ref. Hoje `retry` repete a mesma etapa.
- **Remover o fan-out `memory_observation` por etapa.** Emitir um único `retrospective` ao fim do run, ou em `failed` terminal.
- Guarda de loop: `iteration > run_caps` → `failed(loop_cap)`.

## 4. Canal humano e relatório (`core/line/human.py`)
- `HumanRequest{kind: grill|secret|account|repo_setting|commercial_acceptance|infra, run_id, blocking_stage, guide_md, probe_cmd}`. Persiste via `ManualDependency` (`core/workflow/contracts.py`) e `manual_resolution` (HF-08-05), que já fazem probe e retomada.
- `guide_md` é gerado pelo agente read-only com a instrução do AGENTS.md (passo a passo tela a tela, todos os campos). O envio vai pelo owner bot (`core/notifications/service.py::notify`).
- A resposta ou o probe verde re-enfileira **só** o job bloqueado. Os irmãos seguem.
- Mensagens ao owner, e só estas: (a) perguntas do Grill (1 por demanda), (b) HumanRequest, (c) entregue (PR, URL, SHA, custo, premissas assumidas), (d) falha terminal com resumo e próximo passo sugerido.

## 5. Retrospective (baixa prioridade, nunca bloqueia)
Agente read-only barato (`distill`) lê o REPORT e os logs do run e anexa ≤5 linhas em `.darkfac/LESSONS.md` do repo alvo (commit direto no default via PR pequeno, ou na próxima branch). Mais o registro de custo/iterações em `telemetry.db`. Isso já alimenta `{lessons}` nos prompts (HF-27-04). A trilha HF-10/HF-25 pode consumir isso depois.

## Aceite
- E2E local com `SqliteControlStore`, repo bare, `gh` falso, adapter de deploy falso e agente falso: uma demanda passa por todas as etapas com `output_refs` reais (SHAs e URL do PR falso). Nenhum `deterministic_mock`.
- Uma etapa sem handler dá `missing_handler` e nenhum sucessor.
- `retry:development` a partir do review cria development `iteration=1`.
- Worker sem `harness:*` não claima development, e o painel acusa ausência.
- O número de jobs por run cai para as etapas da linha + 1 retrospective.
