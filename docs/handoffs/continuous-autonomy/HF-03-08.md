## Escopo fechado

- O worker cloud despacha pelo registry real de handlers por estágio (`core.line.bindings.build_line_registry`, integrado via HF-27-08); não há mais fabricação de sucesso genérico no caminho de produção.
- `core.workflow.handlers.DefaultStageHandler._default_execute` (o handler legado de `build_handlers()`, usado só pelos testes/HF-05) falha com `StageResult(outcome="failed", cause_code="missing_stage_service")` quando não há serviço vinculado — não inventa mais `output_refs`/`evidence_refs`.
- `core.orchestrator.cloud_coordinator.CloudCoordinator.create_app`: `/healthz` é liveness-only (sem dado sensível); `/readyz`, `/status`, `POST /api/v1/tasks` e `GET /api/v1/tasks/{run_id}` exigem `Authorization: Bearer <token>` (`DARKFAC_COORDINATOR_API_TOKEN`, mínimo 32 caracteres, comparado com `secrets.compare_digest`); sem token configurado a rota responde 503 (fail-closed), com token errado responde 401. Intake fica desligado por padrão (`DARKFAC_INTAKE_ENABLED=false`) e só aceita `project_id == DARKFAC_ALLOWED_PROJECT_ID` (default `darkfac`); consultar o status de um run de outro projeto responde 404, não vaza dado de outro projeto. A checagem `--status` da CLI (usada pelo healthcheck do container) chama `inspect_status()` diretamente, sem HTTP — não foi alterada.
- `scripts/dispatch_cloud_task.py` (único cliente HTTP do coordenador) envia `Authorization: Bearer $DARKFAC_COORDINATOR_API_TOKEN` quando essa variável está definida.
- `deploy/dokploy/docker-compose.cloud.yml`: a porta 8001 do coordenador passa a publicar só em loopback (`127.0.0.1:8001:8001`); as três variáveis acima (`DARKFAC_COORDINATOR_API_TOKEN`, `DARKFAC_INTAKE_ENABLED`, `DARKFAC_ALLOWED_PROJECT_ID`) foram adicionadas ao serviço do coordenador.

## Ajuste deliberado em relação ao ACTIVATION-RESULT original

O `ACTIVATION-RESULT.md` histórico (preflight de 20–21/09) e o branch nunca mesclado `codex/hf-03-08-activation` pediam também **pin de imagem por digest sha256** (`DARKFAC_CLOUD_IMAGE_DIGEST`) no Compose. Esse item **não foi portado**: não existe pipeline de CI publicando imagens em GHCR neste repositório — o Dokploy builda a imagem direto do SHA do `main` a cada push (`build: context: https://github.com/GCamposGit/DarkFactory.git#main`, `image: ghcr.io/gcamposgit/darkfac-cloud:latest`, inalterados). Fixar por digest exigiria um passo de publicação que não existe e quebraria o deploy autônomo atual. Fica como **item residual deferido**, junto de HF-27-09 (que é quem tem ownership de `deploy/dokploy/env.cloud.example`) — ver `required_before_live_activation` em `activation-receipts.json`.
