## Especificação fechada do primeiro incremento

Este apêndice é normativo e prevalece sobre a descrição curta do índice. Criar somente
`core/workflow/effective_policy.py` e `tests/test_effective_policy.py`. Não mudar política
ativa, CLI, HTTP, arquivo de configuração ou regra de merge neste incremento. A integração
com grants autenticados pertence a HF-26-02. O resolvedor é uma função pura; não precisa
credencial, acesso cloud, modelo adicional ou infraestrutura.

Todos os modelos: Pydantic v2, frozen=True, extra=forbid, strings não vazias, datetime UTC
com timezone obrigatório, custos Decimal não negativos e finitos (serialização como string).
Enums são str Enum. As coleções são tuple; não usar defaults mutáveis.

```python
class Operation(str, Enum):
    PLAN = 'plan'
    IMPLEMENT = 'implement'
    VALIDATE = 'validate'
    MERGE = 'merge'
    DEPLOY_STAGING = 'deploy_staging'
    DEPLOY_PRODUCTION = 'deploy_production'
    READ_SECRET = 'read_secret'
    SPEND = 'spend'

class PolicyRequest(BaseModel):
    project_id: str
    operation: Operation
    scope_ref: str
    candidate_digest: str
    policy_version: str
    estimated_cost_usd: Decimal

class PolicyGrant(BaseModel):
    grant_id: str
    project_id: str
    operation: Operation
    scope_ref: str
    policy_version: str
    expires_at: datetime

class AcceptanceProof(BaseModel):
    project_id: str
    candidate_digest: str
    receipt_ref: str
    expires_at: datetime

class PolicyContext(BaseModel):
    project_id: str
    policy_version: str
    now: datetime
    paused: bool
    cancelled: bool
    commercial_paid: bool
    grants: tuple[PolicyGrant, ...]
    trusted_grant_ids: tuple[str, ...]
    explicit_denials: tuple[Operation, ...]
    failed_gate_refs: tuple[str, ...]
    remaining_budget_usd: Decimal
    acceptance: AcceptanceProof | None
    trusted_receipt_refs: tuple[str, ...]

class PolicyDecision(BaseModel):
    status: Literal['allowed', 'blocked_policy', 'waiting_dependency',
                    'waiting_budget', 'paused', 'cancelled']
    reason_code: str
    matched_grant_id: str | None
    blocking_refs: tuple[str, ...]
    project_id: str
    operation: Operation
    scope_ref: str
    candidate_digest: str
    policy_version: str

# API única pública de decisão:
def resolve_effective_policy(request: PolicyRequest, context: PolicyContext) -> PolicyDecision: ...
```

Os nomes acima são tipos NOVOS a criar, não stubs autorizados na entrega. Implementar
validações antes da função: rejeitar grants com IDs duplicados/conflitantes; trusted IDs
inexistentes; receipts duplicados; datetime ingênuo; custo NaN/infinito/negativo. Digest é
string opaca não vazia, pois o domínio não impõe formato de algoritmo ao adapter.
Não incluir token, valor de segredo, URL ou senha nestes contratos.

`context` é entrada da fronteira confiável do supervisor, nunca payload da demanda;
a função pura não autentica o criador do contexto. A unidade 02 deverá carregar grants e
recibos de store confiável, sem aceitar trusted_grant_ids enviados pelo cliente. Este
incremento não deve expor HTTP para que o usuário fabrique um contexto confiável.

Precedência determinística (primeiro motivo vence; blocking_refs ordenado):

1. project_id/policy_version divergentes → blocked_policy / context_mismatch.
2. cancelled → cancelled / explicit_cancel; paused → paused / explicit_pause.
3. operação em explicit_denials → blocked_policy / explicit_deny.
4. failed_gate_refs não vazio → waiting_dependency / gate_failed, preservando refs.
5. estimated_cost_usd maior que remaining_budget_usd → waiting_budget / ceiling_exceeded.
6. Se commercial_paid e deploy_production: acceptance deve ter projeto/digest exatos,
   receipt_ref em trusted_receipt_refs e expires_at > now. Caso contrário,
   waiting_dependency / client_acceptance_required. Não exigir para staging/merge.
7. Selecionar grant com projeto/operação/scope_ref/policy_version exatos, grant_id confiável
   e expires_at > now. Mais de um elegível: menor grant_id lexicográfico (determinismo).
   Sem grant → blocked_policy / authorization_missing. Nenhum wildcard de escopo/projeto.
8. Com grant elegível → allowed / authorized, matched_grant_id preenchido.

Não existe bypass por classe A/B/C/D, `approved=true`, modelo escolhido, orçamento zero
ou presença de relatório. O loader do projeto gera grants conforme intenção já autorizada,
sem novo aceite por ticket; a função não cria grants. Pausa/cancelamento nunca são superados.
A decisão vincula todos os campos identificadores do request, inclusive scope/digest, para
que HF-26-02 rejeite replay para outra operação. Falta de grant não cria ManualDependency
por si só: reconciliar política e alternativas primeiro.

Exemplo válido: projeto darkfac, operation implement, scope_ref ticket/HF-26-01,
policy v1, custo 0, saldo 0, grant g1 correspondente confiável até 2099-01-01 UTC,
now 2026-09-18 UTC, sem deny/gates/pause/cancel → allowed(g1). Repetir é igual e não muta context.
Exemplos inválidos: grant de jarvis; grant expirando exatamente now; token g1 não confiável;
custo 1 com saldo 0; deploy_production comercial com receipt de digest anterior; grant de
merge usado para deploy. Todos negam com motivo específico. Learning Pack não é campo nem gate.

Aceites focais obrigatórios: tabela parametrizada das oito regras e limites temporais;
precedência deny sobre grant e pausa sobre custo; grant duplicado/rejeição de extra;
Decimal round-trip; caso comercial staging permitido/produção bloqueada; prova correta
libera mesmo digest; request de outro scope não reutiliza decisão; determinismo e ausência
de mutação/IO (mock de socket/open/subprocess faz falhar caso invocados).
