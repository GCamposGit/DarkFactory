## Contratos fechados

Implementar Pydantic v2 com `extra='forbid'`, UTC com timezone, IDs não vazios, `Path` e logging. Domínio não importa FastAPI nem executa I/O. Campos desconhecidos de uma fonte externa são preservados apenas por referência ao arquivo, não copiados para metadata arbitrária do domínio.

Um relatório de implementação cria `reported`; arquivo existir pode confirmar presença do artefato, nunca comportamento. `verified` de integração exige recibo remoto com repositório/base/SHA/merge correspondente; `verified` de operação vale só para a capacidade sondada, ambiente e instante observados. Um `GET /health` não prova execução de testes nem isolamento de jobs.

### Regras de reconciliação, em ordem

1. Inventariar fontes com conteúdo limitado a 2 MiB por arquivo e UTF-8 estrito. Rejeitar link simbólico que escape da raiz. Fonte ausente obrigatória torna snapshot parcial e bloqueia HF-02 somente se necessária à comparação do runtime.
2. Extrair linhas exclusivamente de tabelas com cabeçalhos declarados no catálogo. Para DF/RM usar IDs completos; para HF separar seção Onda 1/Onda 2. Remover apenas formatação Markdown de células; preservar o texto original por locator. Cabeçalho inesperado gera `SOURCE_SCHEMA_CHANGED`, não adivinhar nova tabela.
3. JSON de roadmap exige `items` como lista, `id`/`title`; dependências aceitam apenas formas explicitamente mapeadas de cada fonte. IDs duplicados dentro da mesma fonte são erro. Duplicata entre fontes vira um item com claims distintos.
4. Associar relatório pelo ID no título/linha de identidade e catálogo. Uma menção incidental no corpo não conclui outro ticket. `DF-07 & DF-08` exige mapeamento explícito para os dois. USR-16 complementa INFRA-10 por vínculo declarado, sem fundir as identidades.
5. Um resumo qualitativo (por exemplo, “sem iniciar automação funcional”) é convertido em claim apenas pelo registro curado de evidências do ticket HF-01-01. O coletor não interpreta semântica de texto livre com LLM nem usa palavras positivas isoladas como veredito.
6. Comparar claims por dimensão e escopo. Não escolher silenciosamente a data mais recente se faltam revisão, SHA ou equivalência de ambiente. Conflitos permanecem visíveis até evidência específica resolver o mesmo escopo.
7. Declaração explícita do owner “PostgreSQL funciona” fica `operation=reported`, sem negar a declaração; acesso técnico ainda não conferido recebe pendência independente. Probes atuais não apagam evidência histórica, apenas acrescentam observações.
8. Separar `capability_present`, `remote_delivery_unknown`, `service_endpoint_missing`, `source_conflict`, `partial_ticket_coverage`, `access_required`, `source_unstable`. Não usar “bug confirmado” quando só há divergência de versão.
9. Detectar dependência órfã/ciclo usando IDs normalizados; vínculos de evidência não são dependências de execução. O núcleo não altera status das fontes.
10. Ordenar por fonte/ID; fingerprint = SHA-256 do JSON canônico das identidades, hashes de fontes e política, sem horário de coleta. Snapshot lógico idêntico produz fingerprint idêntico; `observed_at` pode mudar. Nunca gravar por cima de uma saída existente sem flag explícita.

## Sondagens limitadas e acesso

Rede é opt-in por configuração validada contendo IDs e URLs literais. Permitir GET dos endpoints já identificados do Hub e worker, com timeout de 3 s por destino, no máximo uma tentativa e resposta até 64 KiB; sem redirects automáticos. O executor confirma os destinos no catálogo vigente antes do envio. Não descobrir portas por varredura.

Para `/api/tasks/dashboard`, guardar status HTTP, tipo de payload e um erro classificado, sem estado detalhado de demandas de outros projetos. 404 significa contrato indisponível naquele serviço, não ausência de código no repositório. Para n8n, o link genérico não é alvo de health check; ausência de URL fica `access_required`/`unknown`. Dokploy sem sessão não é instalação ausente. Para PostgreSQL, o HF-01 só registra declaração do owner e parâmetros de conexão disponíveis sem valores secretos; conexão de teste pertence ao HF-02-01 e usa banco descartável.

Recibos GitHub são metadados sanitizados obtidos por leitura autorizada em sessão executora: repo, PR, head/base/merge SHA, estado, horário e conclusão dos checks. Sem acesso, registrar `remote_delivery_unknown`; não bloquear a baseline local inteira. Não fazer push/merge de outros tickets para reconciliar seu status.

Um recibo importado sem proveniência conferida permanece `reported`. Promover integração a `verified` exige leitura remota pelo coletor confiável ou atestação conferida do supervisor; um campo `verified=true` no JSON não basta. A baseline é evidência de auditoria, não autorização para deploy.
