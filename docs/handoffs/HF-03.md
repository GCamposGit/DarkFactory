Plano v1.0, 11/09/2026. Planejador: modelo de alta inteligência (Astra).  
Origem: Seção 12 do [Plano Híbrido](../HYBRID_WORKFLOW_PLAN_2026-09-08.md), [ADR-HF-001](../decisions/ADR-HF-001-runtime.md) e [HF-03-INPUTS](HF-03-INPUTS.md).  
Estado: **especificado para handoff condicionado ao HF-02**.

Aplicar [política obrigatória de handoff](../HANDOFF_POLICY.md). O HF-03 materializa a infraestrutura de controle remoto e o worker isolado na Hetzner Cloud VPS (`darkfac-vps-primary`, IP 178.105.73.168 / Tailscale 100.83.176.60), reaproveitando o Dokploy PaaS (INFRA-06) e o PostgreSQL multi-tenant (INFRA-07), mantendo o domínio DarkFac intacto e o clone offline preservado.

---

## 1. Decisões Resolvidas para o Implementador

1. **Reaproveitamento de Infraestrutura Existente**: Usar a VPS Hetzner CX23 já provisionada em Falkenstein e o Dokploy PaaS já instalado em `https://dokploy.ggcampos.com`. Não contratar novas VPSs, instâncias de Kubernetes ou clusters gerenciados.
2. **Banco Descartável Namespaced**: O banco de dados para o coordenador/worker cloud deve ter o prefixo `darkfac_hf02_` (ex: `darkfac_hf02_prod` ou `darkfac_hf02_lab`). Proibido usar banco de cliente ou o banco interno de administração do Dokploy.
3. **Usuário com Menor Privilégio**: Conexão realizada por usuário `darkfac_worker`, sem permissões `SUPERUSER`, `CREATEDB` ou `CREATEROLE`. Proibido usar usuário `postgres` padrão.
4. **Isolamento de Credenciais**: DSNs nunca devem ser commitadas, impressas em logs ou serializadas em manifestos. Configuração exclusivamente via variável de ambiente `DARKFAC_HF02_DATABASE_URL`.
5. **Runtime Pinned**: Versão oficial do DBOS fixada em `2.31.1` com `psycopg[binary] >= 3.2.0, < 3.3.0`.
6. **Concorrência Bounded Declarativa**: O coordenador cloud deve inicializar com limite estrito de **2 slots simultâneos** de execução, configurável via variável declarativa (`DARKFAC_MAX_CONCURRENT_SLOTS=2`), compatível com os 4 GB RAM da VPS e escalável no futuro.
7. **Independência de Hardware Local**: O critério central do HF-03 é provar que a fábrica cloud continua operando e retoma workflows mesmo com o notebook de desenvolvimento e o servidor local desligados.

## 2. Dependência Manual do Owner e Probes de Retomada

Conforme a regra E4 de `HYBRID_AUTONOMY_REQUIREMENTS.md`, a criação do banco de dados na VPS é responsabilidade exclusiva do owner via painel web Dokploy:

### Passo 1: Acessar o Dokploy
Acessar `https://dokploy.ggcampos.com` (ou via IP Tailscale `http://100.83.176.60:3000`).

### Passo 2: Criar o Banco e Usuário no PostgreSQL Existente
No serviço PostgreSQL do Dokploy:
1. Criar novo banco: `darkfac_hf02_prod` (ou `darkfac_hf02_lab`).
2. Criar novo usuário: `darkfac_worker` com uma senha forte.
3. Conceder permissões: `GRANT ALL PRIVILEGES ON DATABASE darkfac_hf02_prod TO darkfac_worker;`.

### Passo 3: Fornecer a URL de Conexão
Definir a variável de ambiente:
```text
DARKFAC_HF02_DATABASE_URL=postgresql://darkfac_worker:<SENHA>@<HOST_INTERNO_DOKPLOY_OU_TAILSCALE>:5432/darkfac_hf02_prod
```

### Probe Automatizado de Retomada
Para validar se a configuração manual foi concluída com sucesso antes de iniciar os testes da nuvem:
```powershell
python C:\dev\DarkFac\spikes\runtime_choice\cli.py preflight
```
*Veredito de Sucesso*: Retorna código `0` com `"dbos_postgres": {"database_connection": "ready", "status": "ready"}`.

## 3. Tickets de Execução Fatiados

### HF-03-01 — Manifesto de Implantação Dokploy e Configuração Cloud
- **Papel**: Econômico.
- **Arquivos principais**: novos `deploy/docker-compose.cloud.yml`, `deploy/Dockerfile.worker`, `deploy/env.cloud.template`, `tests/test_cloud_deployment_manifest.py`.
- **Escopo**: Declarar serviço `darkfac-coordinator` e `darkfac-worker` namespaced na rede Dokploy, montagem de volumes para `.factory/artifacts/` e `.factory/test_logs/`, política `restart: unless-stopped` e limites de memória (512 MiB reserva, 1.5 GiB limite).
- **Validação**: `python -m pytest tests/test_cloud_deployment_manifest.py -v`.

### HF-03-02 — Conector e Probe de Prontidão do Banco Descartável
- **Papel**: Econômico.
- **Arquivos principais**: novos `core/orchestrator/cloud_db.py`, `tests/test_cloud_db.py`.
- **Escopo**: Implementar probe determinístico de conectividade com retry exponencial, verificação de versão PostgreSQL (>= 16), validação de usuário unprivileged (`current_user != 'postgres'`) e isolamento de DSN.
- **Validação**: `python -m pytest tests/test_cloud_db.py -v`.

### HF-03-03 — Inicialização do Coordenador Cloud DBOS
- **Papel**: Econômico.
- **Arquivos principais**: novos `core/orchestrator/cloud_coordinator.py`, `tests/test_cloud_coordinator.py`.
- **Escopo**: Inicializar `DBOS(config=...)` com `application_version='v1'`, registrar filas de sistema, auto-recuperação pós-boot para workflows pendentes e escuta de eventos.
- **Validação**: `python -m pytest tests/test_cloud_coordinator.py -v`.

### HF-03-04 — Worker Cloud Isolado e Fencing de Concorrência
- **Papel**: Econômico.
- **Arquivos principais**: novos `core/orchestrator/cloud_worker.py`, `tests/test_cloud_worker.py`.
- **Escopo**: Implementar worker em container desacoplado, recebendo tarefas da fila durável do DBOS, executando etapas computacionais determinísticas e respeitando limite configurável de slots (`DARKFAC_MAX_CONCURRENT_SLOTS`).
- **Validação**: `python -m pytest tests/test_cloud_worker.py -v`.

### HF-03-05 — Armazenamento Durável de Artefatos e Isolamento
- **Papel**: Econômico.
- **Arquivos principais**: novos `core/orchestrator/cloud_artifacts.py`, `tests/test_cloud_artifacts.py`.
- **Escopo**: Gravar artefatos grandes no volume de disco sob `.factory/artifacts/<workflow_id>/`, registrando no DBOS apenas digests SHA-256 e caminhos sanitizados relativos (`artifact_refs`), preparando a abstração para integração com Cloudflare R2 no HF-12.
- **Validação**: `python -m pytest tests/test_cloud_artifacts.py -v`.

### HF-03-06 — Ensaio de Resiliência Cloud e Relatório de Prontidão
- **Papel**: Econômico.
- **Arquivos principais**: `.factory/reports/hf-03-cloud-readiness-report.md`, `tests/test_cloud_e2e_readiness.py`.
- **Escopo**: Executar workflow síncrono e workflow com espera de aprovação na nuvem; matar o container do coordenador no meio da execução; reiniciar container; confirmar que o workflow é retomado sem duplicar efeitos colaterais e atinge sucesso.
- **Validação**: `python -m pytest tests/test_cloud_e2e_readiness.py -v` e `python core/harness/runner.py --quick`.

## 4. Critérios de Aceitação do Pacote HF-03

1. **E1 (Isolamento de Credenciais)**: Nenhuma DSN, senha ou host interno aparece em commits, logs ou tracebacks.
2. **E2 (Probe de Conexão Funcional)**: `cli.py preflight` reporta `ready` quando a variável `DARKFAC_HF02_DATABASE_URL` estiver configurada.
3. **E3 (Persistência e Crash Recovery)**: Reiniciar o container cloud não perde estado de workflows em voo e retoma checkpoints confirmados.
4. **E4 (Execução Independente)**: A nuvem consegue processar um workflow completo com o notebook e máquina de desenvolvimento completamente desconectados.
5. **E5 (Preservação do Modo Offline)**: A suíte de testes padrão da Dark Factory continua 100% verde sem requerer acesso à internet ou ao PostgreSQL da VPS.
